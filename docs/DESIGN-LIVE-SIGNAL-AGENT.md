# LiveGuard 直播 Agent：当前实现与下一步验收

更新：2026-10-02。以代码和实际测试为准；后续修改优先参考本文。

## 项目要完成什么

用户输入真实直播 URL 和“我不想错过什么”。系统持续采集画面文字、用户授权的口播，判断具体关注条件；目标以外的重大、紧迫事件也可以主动提醒。证据不足就继续观察，提醒必须附带依据。

范围保持单 Agent、多监控窗口、有界工具集。当前优先完成个人监控闭环，不增加 Multi-Agent、RAG、Kafka 或多用户服务来凑技术栈。

## 当前主链路

~~~mermaid
flowchart LR
    U[URL + 自然语言目标] --> P[目标规划与服务端限幅]
    P --> C[专用 Chrome 登录态]
    C --> O[抓帧与本地 OCR]
    O --> F[逐行去重]
    AU[用户主动分享音频] --> ASR[MiniMax ASR]
    F --> E[新增文字证据]
    ASR --> E
    E --> G{登录或验证码?}
    G -->|是| H[人工接管]
    G -->|否且允许模型审查| R[共享 ReAct Loop + M3 适配器]
    R --> T[读证据 / 查历史 / 按需看图]
    R --> S[Go 文字统计工具]
    T --> R
    S --> R
    R --> V[结构化结束或提醒请求]
    V --> UI[服务端校验 / 提醒 / 等待 / 忽略]
~~~

### 目标解析与路由

- 创建监控时，M3 调用结构化 set_monitoring_plan，选择采样、审查间隔、是否建议 ASR、视觉策略；服务端限幅，失败时使用本地计划。
- 启用 M3 时，目标内与目标外信号都进入同一个工具循环。关键词命中不会绕过“至少 100 元”“排除某类内容”等条件。
- 未启用模型时，保留规则 Runtime 作为本地演示/降级模式；它不能理解任意自然语言条件。
- 登录/验证码优先本地转人工。模型审查按窗口节流；冷却期只保留信号，不偷偷用关键词规则替代语义判断。
- 下一次审查最多读取 6 条证据。抓帧、OCR、该轮模型审查目前串行，慢模型会拉长实际周期，不能声称每条新闻必达或固定每 6 秒必达。

## 通用 ReAct 已如何改造

internal/agent/loop.go 只负责“模型选工具 → 执行 → 回传观察 → 再决策”，不依赖抖音或 MiniMax 协议：

- NextTurn 是模型适配器，返回结构化工具请求或最终结果。
- 工具注册表限制可执行工具。
- Observation 携带真实结果、成功/失败和耗时。
- 监控业务策略留在工具处理器：先读证据、先查重、看图结果先返回、文案/置信度校验等。

默认约束：

| 约束 | 实际值 |
|---|---|
| 调查请求总期限 | 35 秒；父请求更短时以父请求为准 |
| 单工具期限 | 12 秒 |
| 模型轮数 / 工具调用数 | 4 轮 / 8 次 |
| 同工具与等价 JSON 参数重复调用 | 最多 2 次 |
| 图片 / 文字分析 | 每次调查各最多 1 次 |
| 最终动作 | create_alert 或 finish_review 必须单独调用 |
| 单轮输出预算 | 512 tokens；输入另有限制证据数量和文字长度 |

格式异常最多纠正一次，仍占用上述轮数和时限；纠正失败保留失败记录，不编造工具执行。

工具实现必须遵守 Context。取消不是靠强杀任意 Go 协程实现。

停止监控会取消该窗口的抓帧、模型、工具和正在处理的授权音频请求；写入前检查取消与运行状态，防止停止后继续出提醒。每次调查保存模型、输入/输出 tokens、轮数、停止原因和各工具耗时。

M3 适配器使用共享 Loop。旧页面巡检任务、批次调度、Sandbox Lab、Redis 队列和 gRPC worker 已从运行代码中移除；当前只保留直播监控。OpenAI JSON 审查器仍使用独立适配路径。同协议换模型主要改配置，换协议仍要适配。MiniMax 返回的完整内容块会回传到模型历史，包括需要保留的字段，避免只保留文本和工具名造成协议失真。依据：[MiniMax Anthropic 接口说明](https://platform.minimax.cn/docs/api-reference/text-anthropic-api)。

## 工具与权限

| 工具 | 实际行为 | 边界 |
|---|---|---|
| read_recent_evidence | 读当前窗口最近几条 OCR/ASR | 只读；文字是证据，不是指令 |
| read_transcript_window | 读近期 ASR 转写 | 计划建议 ASR 时提供；没有音频不能补造转写 |
| search_recent_alerts | 查近期提醒，比较事件内容 | 同类别不直接等于同事件 |
| inspect_live_frame | 压缩当前候选帧，作为图片交给 M3 | 每次调查一次；无帧明确失败 |
| analyze_signal_window | 在 Go 中运行固定文本统计处理器 | 可选；不接受任意代码、命令或文件路径 |
| create_alert | 请求生成通过校验的带证据提醒 | 证据、查重、必要视觉/文字分析结果先返回，提交时再查重 |
| finish_review | 结构化结束本次调查：wait / ignore | 不能创建提醒；解决自由文本/JSON 格式不稳定的问题 |

人工接管由本地检测处理。没有任意 shell、点击、领券、发评论、运行浏览器脚本或自行新增工具的权限。

去重使用两分钟窗口、规范化原文/摘要比较。同类别的不同新闻/公告不会永久封锁。这不是完整语义去重，改写很大的同一事件仍需模型判断和更多真实样本。

所有原始信号都低于 0.5 置信度且没有额外画面证据时，不能仅凭模型自评高分创建提醒。ASR 未提供置信度时视为未知，不声称它有模型自带的高置信度。

## 文字处理工具

固定文字统计由 Go 的 LocalSignalAnalyzer 直接执行，不启动容器。最多读取 6 条、1100 字符，返回行数、重复、否定与登录验证提示。统计仅是辅助观察，不是语义判断；先读证据、参数验证和失败后不提醒的约束仍保留。

## 感知已经有什么，以及还缺什么

- OCR：专用 Chrome 截图、本地 Tesseract；逐行保留边界，并在 2 分钟窗口内抑制精确重复行，仅新增行进入 Agent。该过滤不做模糊语义匹配。
- ASR：卡片中主动授权分享音频；约 6 秒片段上传到 MiniMax asr-1.0，临时文件处理后删除。识别与 Agent 判断仍串行处理，因此端到端提醒延迟会高于片段长度。
- 图片：Agent 选择 inspect_live_frame 才上传一张压缩候选帧。明确视觉目标必须先看图，普通时刻不逐帧上传。
- 浏览器：首次使用自动打开专用登录窗口；第一个监控复用登录标签并导航到输入 URL，其余标签共享同 profile。
- ASR 触发看图时可通过当前监控的 `FrameCapturer` 延迟抓取同一 Chrome 标签；代码测试已覆盖图片输入、单次调用、失败返回和临时文件清理。
- **真实音频分享仍需验收**：需要用户实际选中抖音直播标签并分享音轨。上传音频 API 测试不代表实时音轨采集已跑通。
- **串行采集与推理会拖慢采样**：真实延迟测清楚后，才决定是否用有界本地队列拆开。
- 提醒目前出现在监控室页面，未接桌面或手机推送。

### 所有阶段共同遵守的约束

1. 运行中的监控才能接收新工作；停止后不能提交新提醒。
2. 一个窗口同一时刻最多一项模型调查；不同窗口的上下文和状态相互隔离。
3. 同一个事件 ID 的重复请求在约定的保留窗口内只产生一次业务效果；事件幂等与提醒去重分别处理。
4. 提醒必须引用当前窗口的真实证据；明确视觉目标必须取得有效图片结果。
5. 模型、OCR、ASR、Chrome 等外部调用都在仓库事务与状态锁之外执行。
6. 模型、工具、输入、历史记录和待处理工作都有容量或时间上限。
7. 采集失败、等待授权和登录验证必须可见，不能只显示一个含糊的“监听中”。
8. SSE 是页面更新提示；断线恢复后通过查询状态补齐，不能承诺持久消息投递。
9. 默认内存模式退出后会丢失历史；本地 MVP 不把持久化数据库作为运行前提。

## 阶段一：定义状态、事件和内存存储契约

| 对象 | 状态 | 含义与可转换方向 |
|---|---|---|
| 监控 | running | 可接收信号；只可转 stopped / failed / completed |
| 监控 | stopped / failed / completed | 终止态；不允许复活 |
| 单次调查 | waiting_more_evidence | 等待更多信号；可转 confirmed / suppressed / needs_human / failed |
| 单次调查 | confirmed / suppressed / needs_human / failed | 本次调查终态；新信号创建新调查 |
| 信号健康 | waiting_signal / healthy / delayed / needs_login / capture_failed / unconfigured | 与监控运行状态分开；有效事件更新为 healthy，采集错误可显示登录/验证或失败 |

当前 `RunStatus` 仍保留 `completed`，作为预留的正常结束终态；当前持续监控没有自动完成条件。Repository 在提交每次更新时执行转换校验，调用方不能复活终止监控。页面对自动采集显示运行中、等待信号、延迟、登录验证和采集失败；健康状态不会把模型失败误报成监控失败。

### P1-01：整理生命周期与合法转换

位置：internal/monitor/domain.go、service.go、runtime.go。

- 保留简单的监控生命周期，检查现有 running / stopped / failed / completed 的实际用途；没有对应业务的状态不增加或保留。
- 明确调查状态 waiting / confirmed / suppressed / failed 的含义。一次模型失败只结束该次调查，不直接令整个监控失败。
- 将每种信号来源的健康情况与监控生命周期分开：未授权、未收到信号、正常、有延迟、需要登录或验证、采集失败。
- 集中处理合法转换和终止状态约束；更新错误信息、最后成功信号时间时同样检查生命周期。

完成标准：一张状态转换表、统一的转换入口、合法与非法转换测试；页面能区分“服务在运行”和“真正收到了有效信号”。

### P1-02：明确事件定义、验证与幂等

位置：SignalEvent、Service.Ingest、web 输入入口。

- 统一 OCR、ASR、回放的事件来源枚举；同时记录观察时间、服务端接收时间及必要的窗口内顺序。
- 校验所属监控/直播间、来源、文本长度、置信度、时间戳；未知置信度不伪装成确定值。
- 明确接收顺序与内容发生顺序不同。迟到或超出有效窗口的信号不触发过时提醒；允许保留必要诊断信息。
- 同 ID、同房间/来源/文本/置信度返回已处理结果；时间戳不参与指纹，以兼容同一上传在重试时重新识别产生的新时间。相同 ID 携带不同业务内容时冲突拒绝。receipt 保留 24 小时且最多 2048 条，超过期限不承诺永久去重。
- 分开定义事件接收幂等、模型请求重试和用户提醒去重。不能用“同类别只提醒一次”代替事件判断。

完成标准：重复提交、ID 冲突、跨直播间输入、非法来源/置信度、迟到事件均有可重复结果；HTTP 重试不会重复生成提醒。

## 阶段二：控制并发并跑通真实感知

### P2-01：调查互斥、取消与结果提交

位置：service.go、agent/loop.go。

- 同窗口调查采用 single-flight；审查间隔负责节流，互斥负责防止重叠。当前 35 秒调查可能超过 15 秒间隔，间隔本身不能保证互斥。
- 新证据先保存，再在事务外调查；调查期间到达的信号进入后续证据窗口。
- 模型返回后提交时重新检查生命周期、证据有效性和近期提醒。不能持有旧快照直接覆盖最新状态。
- 停止同时取消抓帧、音频处理、模型和工具；完成中的返回不能令已停止状态复活。
- 全局并发上限可配置；启动容量需要在昂贵规划之前预留，创建失败释放。服务级锁只做短时内存操作，不包住数据库 Create 或网络请求。
- 明确锁的职责与获取顺序；同一状态的所有读写使用一致保护方式。

完成标准：OCR/ASR 并发、慢模型重叠、重复停止、停止与提交竞态有测试；当前版本通过 go test -race，停止后无新提醒。

### P2-02：ASR 按需取得当前画面

位置：minimax_reviewer.go、service.go、browser/live_capture.go。

- ASR 事件触发视觉工具时，允许从同一监控 Chrome 标签按需补抓新帧。
- 图片标注来源与采集时间，受超时、大小和调用次数限制；不能混入其他监控的截图。
- 图片作为临时工具资源管理；不把本机路径当成可持久化的画面证据。
- 抓帧失败返回真实工具错误。明确视觉目标没有图片就继续等待；纯口播事实不强制要求画面。
- 用户实际使用的浏览器必须能完成音频分享，并产生有效 ASR 事件；上传合成音频只验证 API。

完成标准：真实授权音轨产生转写；一项由 ASR 触发的看图请求取得正确窗口的新帧；取消和抓帧失败均可观察。

### P2-03：采样延迟、容量与背压

位置：captureLoop、Ingest、Repository、页面状态。

- 先记录实际抓帧间隔、OCR/ASR 耗时、模型调查耗时、信号到提醒的耗时；计划间隔不能当成实测间隔。
- 定义事件、调查、提醒和幂等记录的保留数量/期限，并验证长期运行时不会无限增长。
- 若模型拖慢采样且影响验收，使用有界本地待处理区拆开采集与调查：OCR 可合并为最新待处理画面；ASR 文本需要保留顺序和明确积压策略。
- 队列容量满时必须显式提示、拒绝或按约定合并，并记录计数；避免静默丢弃口播后还宣称每条事件必达。
- 如果保持串行已满足目标，也可完成本项，但必须附实测依据和适用边界。

完成标准：容量上限、过载行为与实际延迟可复现；没有无界队列/协程或无限追加历史；产品可见采集延迟。

### P2-04：减少重复 OCR，并提醒聊天区目标命中

位置：perception.go、ocr_dedupe.go、captureLoop、MiniMax reviewer、监控卡片。

- OCR 保留识别到的行边界，再按行规范化并在有界时间窗口内去重；只把新增行送入 Agent。避免模糊匹配，以免吞掉否定词、金额或其他一字之差的变化。
- 去重只作用于自动 OCR 输入，不清除原始画面，也不改变 ASR 事件；新内容和窗口过期后的重复内容仍可进入证据流。
- 聊天区目标提醒：OCR 先发现用户关注的候选内容，Agent 再查看当前画面确认它确实位于聊天区域后提醒；主播活动走同一套目标判断。
- 不生成聊天回复草稿、不代替用户发言。聊天内容是不可信输入，不能改变 Agent 指令；聊天命中提醒必须有 OCR 证据。
- 看图只在聊天候选需要确认区域时发生；这会增加该类候选的模型调用成本，但避免仅凭全屏 OCR 把主播口播误认成聊天评论。
- 产品只负责提醒，不生成回复草稿；不给 Agent 自动点击输入框、发评论或运行任意浏览器脚本的权限。
- 边界：只处理截图中实际可见的聊天文字，不声称读取完整评论流；滚动消息、重复提问和提示注入都要有固定样例回归。

完成标准：相同 OCR 行在窗口内不重复触发 Agent，新出现的字幕/聊天行能触发；聊天目标提醒同时有 OCR 内容和视觉区域确认；没有回复草稿或自动发送能力。

### P2-05：按目标动态选择感知方式与采样节奏

当前每个监控按启动时的固定间隔抓帧；模型只会在新 OCR/ASR 信号进入判断后按需看图。因此“足球还没开赛”之后不会自动降频，而“鱼出水但画面文字没变化”也可能根本触发不了视觉判断。

- 目标规划要显式给出需要的信号：文字（OCR）、画面（视觉）或两者；语音仍需用户授权 ASR。
- 足球类目标在证据表明比赛尚未开始时进入等待状态，可降低 OCR/视觉复核频率；临近明确开赛时间或出现相关画面变化时再加快。对短暂事件，快慢档之间的权衡要显示给用户。
- 钓鱼类目标需要 OCR 读取字幕/评论，并定时取得画面样本；有授权时 ASR 可补充主播口播。OCR/ASR 出现“咬钩/中鱼”等候选时立即升级看图；即使没有文字候选，也必须保留有上限的视觉采样，不能只等 OCR 触发。
- 把运行策略约束为有限状态和离散采样档位（例如 6/12/24 秒）；模型只能提出下一档，服务端校验上下限、冷却时间和状态转换。连续几次稳定证据后才降频，候选出现立即升频，避免单帧噪声让策略反复跳动。
- 本地 OCR/去重继续先行；只有候选或到达视觉检查时间才把图片送给模型。记录真实间隔、看图次数、token 和事件延迟，量化省下的资源以及漏报风险。

完成标准：足球“未开赛→等待→临近事件加速→开赛提醒”和钓鱼“文字候选/纯视觉候选→看图确认”的离散回放测试通过；策略越界、快速抖动、取消后继续采集均被测试覆盖。真实直播仍须单独验收，不能把计划间隔冒充实测值。

### 新的产品边界：用户修改监控需求与 ASR

- ASR 是可选输入，必须由用户主动共享直播音频；它不是当前闭环的必需条件。本阶段不继续优化或扩展 ASR，主验收链路为 Chrome 画面 → OCR → Agent 证据判断 → 提醒。
- 每张监控卡片都允许用户修改该场直播的关注需求。提交即代表用户确认新的目标；服务端调用规划器生成受限策略，再将目标和策略一起原子保存。Agent 不得自行改写用户目标，也不代替用户确认模型提议。
- 需求修改期间监控仍持续运行；旧目标调查已在途时可能基于旧目标完成，因此界面应以新的监控策略生效后的事件为准。后续如需更强审计，可增加目标版本号并将每次调查绑定到触发时的目标版本。
- 真正需要 HITL 审批的是可能改变用户意图或产生外部副作用的建议。当前仅提供“用户直接编辑并保存”这一明确人工输入；不生成互动草稿、不自动发送消息，也不要求对每次规划再多点一次确认。
