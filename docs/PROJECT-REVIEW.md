# LiveGuard：还需要关注的问题

审视日期：2026-10-14。本页只列仍存在的风险；已完成的 OCR 异步处理、行框、暂停/继续、事件证据引用、队列优先级与公平调度不再重复列为整改项。

## 目前最重要的三个边界

### 1. 截图仍会漏掉短暂评论

截图和 OCR 已分开运行，聊天目标会加快截图；页面也显示截图次数、实际间隔、采集耗时和 OCR 积压跳过数。这能帮助发现采集变慢或处理不过来的情况。

但截图之间出现又消失的评论，以及页面视口外的内容，系统仍然看不到。归档图片只能复查已经拍到的画面，不能补回漏掉的内容。要知道实际漏多少，仍需拿真实直播记录与 LiveGuard 的观测对照测量。

### 2. 观测和保存的截图会一直增加

本地观测现在追加写入 `runtime/liveguard.json.observations.jsonl`，不再每次保存时重写整段历史；PostgreSQL 也保存完整观测。Agent 选中保存的截图放在 `runtime/frames`。这些记录都不会自动删除，这是按“保留流水”的要求处理的。

因此运行越久，数据库和磁盘占用越大。当前还没有占用量提示或容量上限。需要时可以先补占用量显示；是否清理、保留多久，等你决定策略后再做。

### 3. 整场统计和事件状态仍可能不完整

Agent 可以搜索持久观测，并按时间和文字继续翻页；模型上下文只带当前需要的少量结果。一个查询可以同时提交最多 8 个候选短语，后端会合并匹配结果并返回整段筛选范围内的观测记录总数。单次调查仍最多调用搜索 6 次、每页最多返回 12 条；这是 Agent 的输入预算，不是数据库只能查 72 条，也不是精确的模型 token 窗口。

后端给出的总数是“符合这些文字和时间条件的观测条数”，不是去重后的真实事件次数。OCR 重复记录会分别计数，后端也不会自动扩展同义说法。若要回答整场有几次真实事件，仍需判断多个观测是否属于同一件事。系统也没有把“预告、开始、延期、取消、结束”自动连成同一件事的状态记录；这些仍是语义判断风险。

## 其他值得关注的风险

### 高峰时仍可能来不及处理

队列容量有限，现有优先级、等待老化、公平授权和逐条时效能改善拥堵，但不能保证高峰期间每条评论都在有用时限内完成。需要用持续提交的负载验证排队、完成、合并、过期和丢弃数量；只看接口是否接收成功不够。

### 长时间运行没有总模型成本上限

单次调查有调用次数和超时约束，但整个监控 Run 还没有统一累计模型、图片、ASR 和重试成本的上限或清晰展示。长期开着时，调用成本可能持续增加。

### 故障时仍需要更清楚的恢复提示

系统能显示部分登录和采集错误，但用户仍不一定能快速判断故障发生在采集、排队、模型判断还是提醒提交，也缺少每类问题明确的恢复动作。历史数据持久化不等于浏览器、采集任务和未完成调查可以断点续跑。

## 建议先后

1. 用真实直播数据测量截图覆盖间隔和短暂评论漏采情况。
2. 增加观测与截图占用量显示；暂时继续保留全部记录，不自动清理。
3. 如果需要统计真实事件次数，先定义“同一件事”的判定和重复观测去重规则，再考虑事件状态关联；当前后端已能返回完整筛选范围内的匹配观测条数。
4. 再验证高峰负载和长时间运行成本，并补充用户可执行的故障恢复提示。

## 本轮处理与验证

本轮围绕上述风险补了基础能力：采集状态展示、观测流水追加写入、搜索支持多短语合并查询和完整匹配记录数。Agent 仍有每次调查最多 6 次搜索调用的输入预算；存在更多页面时必须按不完整范围解释。没有增加自动清理。

`go build ./...` 已通过。按要求未运行测试套件、真实模型 API 或 Key 验证；编译通过不代表真实直播漏采率、长期磁盘增长或高峰处理能力已完成验收。
