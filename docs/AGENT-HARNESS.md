# LiveGuard 的 Agent Harness：从一条信号到一条提醒

[English](AGENT-HARNESS.en.md) | 简体中文

这份文档专门解释 LiveGuard 的 Agent Harness。它面向刚接触项目的工程师：先说清 Harness 是什么，再沿着一次调查走完代码路径，最后列出状态、工具权限、超时、重试、幂等和评测边界。

> **先记住一句话：**`internal/agent/loop.go` 是通用工具循环；LiveGuard 的完整 Agent Harness 是围绕它搭起来的一条受控调查流程，包含直播领域规则、异步调度、证据校验、结果提交和可观测记录。不能把 Harness 等同于 `loop.go`，也不能把所有这些职责都算成 `loop.go` 自己完成。

## 1. 先用一个简单模型理解它

可以把一次 Agent 调查想成一个受时间和权限限制的实习生：

1. LiveGuard 给它一张当前任务卡：用户目标、触发信号、监控计划和必要的近期证据。
2. 它可以向服务端申请少数几种工具，例如搜索历史观测、查看截图或请求创建提醒。
3. 工具只在服务端执行。结果会回给同一轮调查，供模型继续判断。
4. 轮数、调用数、重复调用、每项执行时间和总时间都有上限。
5. 即使模型提出提醒，Go 服务仍会核对证据、目标版本、监控状态和重复提醒，再决定是否真的保存。

这里的 Harness（执行框架）负责把以上步骤组织起来并守住边界。模型负责解释证据，但不直接操作数据库、浏览器或用户账号。

## 2. “完整 Harness”由哪些部分组成

完整 Harness 是职责组合，不是单个类型或一个文件。按调用顺序看：

| 层 | 代码入口 | 做什么 | 明确不做什么 |
|---|---|---|---|
| 信号接收与排队 | [`service.go`](../internal/monitor/service.go)、[`pending.go`](../internal/monitor/pending.go) | 记录信号、处理事件 ID 去重、放入每个监控自己的有界队列；限制等待量、过期时间和图片暂存 | 不判断直播语义；入队成功不代表模型已调查或提醒已保存 |
| 公平调度 | [`review_gate.go`](../internal/monitor/review_gate.go) | 同一监控一次最多一个调查、全进程限制并发，并给等待调查分配机会 | 不负责工具调用次数或模型请求重试 |
| 领域调查适配器 | [`agent_reviewer.go`](../internal/monitor/agent_reviewer.go) | 为本次 Investigation 准备目标、计划、信号和上下文；创建模型会话及直播工具；运行循环；把输出整理成结构化 Decision | 不直接把模型输出写入 Repository，也不独自保证最终提醒合法 |
| 通用循环内核 | [`loop.go`](../internal/agent/loop.go) | 请求模型、解析工具调用、按白名单执行 Handler、把结果带入下一轮，并执行轮数/调用数/超时/重复调用限制 | 不知道“直播”“聊天区”或“提醒证据”等领域含义 |
| 模型协议适配 | [`model_session.go`](../internal/monitor/model_session.go)、[`messages_model.go`](../internal/monitor/messages_model.go)、[`chat_completions_provider.go`](../internal/monitor/chat_completions_provider.go) | 统一工具调用接口，分别转换成提供方请求格式，并把响应、token、重试次数带回来 | 不决定该不该提醒；也不把不同模型的能力差异变成语义正确性保证 |
| 模型故障保护 | [`circuit_breaker.go`](../internal/agent/circuit_breaker.go)、[`model_settings.go`](../internal/monitor/model_settings.go) | 连续模型错误达到阈值后暂时拒绝新请求，冷却后只放行一个恢复探测 | 不修复凭据、额度或提供方故障；用户仍需查看运行状态和错误 |
| 直播领域工具和规则 | [`review_tools.go`](../internal/monitor/review_tools.go)、[`review_context.go`](../internal/monitor/review_context.go)、[`evidence.go`](../internal/monitor/evidence.go) | 定义能搜什么、何时能看图、提醒必须引用什么证据、如何裁剪上下文 | 不扩大通用循环的工具白名单；模型自己声称“有证据”不算服务端验证 |
| 最终状态与副作用 | [`service.go`](../internal/monitor/service.go)、[`repository.go`](../internal/monitor/repository.go) | 将调查结果映射为状态；再次检查 Run 状态、目标版本、证据、时效和重复项；通过 Repository 保存调查和提醒 | 不保证采集到了直播中发生的一切 |
| 过程记录 | [`domain.go`](../internal/monitor/domain.go)、[`model_trace.go`](../internal/monitor/model_trace.go) 及模型 Adapter | 保存调查状态、工具步骤摘要、时延、token、传输重试、格式修正和停止原因；请求日志补充轮次与超时来源 | 不保存一份可完整重放的私有模型对话；工具参数和原始工具返回不都作为永久审计记录保存 |
| 行为评测与负载测量 | [`eval.go`](../internal/monitor/eval.go)、[`load.go`](../internal/monitor/load.go) | 用固定文字案例衡量判断行为；用 mock Reviewer 测同步和异步服务路径的吞吐、排队和时延 | 不代表真实直播漏采率，也不等于真实模型端到端性能 |

因此，面试中说“我构建了轻量 Agent Harness”时，应该指这条**受控调查路径**；如果只展示 `loop.go`，就漏掉了系统级职责。如果把队列、证据提交或评测都说成 `loop.go` 的能力，又会扩大它的职责。

## 3. 一次 Investigation 怎样从信号走到提醒

`Run` 是长时间存在的一次监控，保存用户目标、当前目标版本、采样计划和历史记录。`Investigation` 是某条信号触发的一次短调查。每次新调查都会新建模型会话，不会偷偷沿用上一条信号的对话；跨调查连续性来自持久化观测和按需历史搜索。

```mermaid
sequenceDiagram
    participant Source as OCR/ASR/画面信号
    participant Service as Monitor Service
    participant Queue as 每 Run 等待队列
    participant Gate as 全局调查门
    participant Reviewer as AgentReviewer
    participant Loop as 通用 Loop
    participant Model as 模型 Adapter
    participant Tool as 直播领域工具
    participant Repo as Repository

    Source->>Service: 提交 SignalEvent
    Service->>Repo: 校验并记录观测与事件回执
    Service->>Queue: 尝试异步入队（仍有效时）
    Service-->>Source: 返回接收处理结果
    Queue->>Gate: 等待公平调度许可
    Gate-->>Queue: 获得本 Run / 全局并发许可
    Queue->>Reviewer: 启动一次有 deadline 的 Investigation
    Reviewer->>Model: 目标、计划、当前信号和有限上下文
    Model-->>Loop: 最终结论，或一个/多个工具调用
    Loop->>Tool: 校验名称、参数、预算和执行期限
    Tool-->>Loop: 工具结果或可恢复的错误说明
    Loop->>Model: 将工具结果追加到本次会话
    Model-->>Loop: 下一轮调用，或最终结构化结果
    Loop-->>Reviewer: 结论、步骤摘要、停止原因和指标
    Reviewer-->>Service: Decision（仅是建议）
    Service->>Service: 再校验状态、目标版本、证据、时效和查重
    Service->>Repo: 保存 Investigation；符合条件才保存 Alert
    Repo-->>Service: 新状态
```

有效信号通过校验并成功入队后，异步 API 会先返回，不等待模型判断完成；这不代表提醒已产生。例外是已经过期的信号：当前实现会留档并记录过期，但 `SubmitSignal` 仍可能返回成功而不入队。同步规则模式则使用另一条确定性处理路径；它不是大模型 Harness 的替代叫法。

## 4. 每一层的职责边界

### 4.1 `agent.Loop`：通用的“模型—工具—模型”循环

`Loop` 不知道 LiveGuard 的业务词汇。它只关心：模型返回了什么、工具是否在允许名单中、参数是否可处理、还剩多少预算，以及是否应该继续。

当前默认限制如下（可通过 `LoopLimits` 覆盖）：

| 限制 | 当前默认 | 作用 |
|---|---:|---|
| 模型轮数 | 6 轮 | 防止同一次调查无限向模型追问 |
| 工具调用数 | 8 次 | 统计已处理的工具观察，限制调查工作量 |
| 相同工具与相同规范参数 | 最多 2 次 | 第 3 次相同调用会被阻止，避免模型原地打转；内容或参数不同的调用按不同指纹计算 |
| 一次调查总时间 | 90 秒 | 超时或父任务取消时停止本次循环 |
| 单个工具时间 | 12 秒 | 慢工具不能无限占用调查时间 |
| 工具参数 JSON | 最多 8 KiB | 限制单个工具请求体积 |
| 终端工具 | 一次回复只能单独调用 | `create_alert` 或 `request_user_input` 执行后，本次循环结束；不让同一批再混入其他动作 |

模型回复中的工具名必须存在于该次调查的白名单，工具 ID 必须存在且不重复。被拒绝或执行失败的调用也会形成结果交回模型，让它有机会纠正或结束；失败不会自动等于成功。

工具 Handler 以 Go 函数形式同步执行。Loop 会给它传入带 12 秒 deadline 的 context，并在函数返回后检查是否超时；这要求 Handler 本身遵守 context 取消。若某个 Handler 永不返回且忽略取消，Loop 不能像操作系统杀进程那样强制停止它。因此这是合作式超时约束，不是隔离不可信代码的沙箱。

终端工具必须单独调用。如果模型把 `create_alert` 和搜索工具放在同一批调用中，终端工具那项会被拒绝并把错误回传；同批其他合法的非终端工具仍可能执行。模型需要看到错误后在预算内重新安排调用。

`Observation` 是一次工具调用的结果记录：本次运行时保存调用信息、工具输出和耗时，并将输出加入同一模型会话。停止原因也会区分模型失败、格式无效、预算耗尽、重复工具、终端动作、正常完成、超时和取消等情况。

注意两个名称容易混淆：`SignalEvent` 是直播业务信号，例如 OCR 识别到的一行文字，带着房间、来源和发生时间，进入观测流水；`agent.Observation` 则是模型在调查中调用工具后得到的一次结果，例如“搜到 3 条历史记录”，只属于这次模型工具循环。

### 4.2 `AgentReviewer`：把通用 Loop 接到 LiveGuard 调查

`AgentReviewer` 做通用循环不知道的事情：

- 为每次调查创建新的 `ModelSession`，整理当前用户目标、计划、当前信号、采样状态和用户指令。
- 从监控状态取有限的近期观测；历史数据由工具按需查询，不把完整历史一次塞进上下文。
- 根据模型能力准备工具列表。模型不支持视觉时，不开放看图工具；明确要求看图的目标会在 Adapter 边界强制执行首次看图要求。
- 将 `review_tools.go` 的领域 Handler 注入通用 Loop，并标记 `create_alert`、`request_user_input` 为终端工具。
- 把通用 Loop 结果转成 Decision，汇总工具步骤、token、模型耗时、传输重试、格式修正数和停止原因。

模型回复上限是每轮 4,096 output tokens。这是**单轮输出上限**，不是完整调查的输入 token 总预算。历史搜索另有字符数预算；系统提示、工具定义、图片和多轮对话的 token 没有统一的 tokenizer 硬上限，因此不能声称“整次请求绝不会超过某个 token 数”。

### 4.3 Model Adapter：隐藏协议差异，不替模型做决定

`ToolModel` / `ModelSession` 给 Reviewer 一个统一接口。MiniMax Messages 和 OpenAI 兼容协议由各自 Adapter 负责鉴权、消息格式、图片编码和工具结果编码。Adapter 保留提供方继续多轮会话所需的原始助手消息字段。

Adapter 会报告输入/输出 token 和传输重试等数据，但不负责判断证据是否能支持提醒。提供方声明支持图片，也不等于模型一定能正确识别图片。

### 4.4 直播领域工具：可用动作有限，业务条件具体

当前调查工具有：

| 工具 | 给 Agent 的能力 | 服务端实际边界 |
|---|---|---|
| `search_observations` | 搜索本监控最近或历史 OCR、ASR、frame、visual 观测 | 每页最多 12 条、最多翻 6 页；按调查共享历史结果字符预算；返回的是观测记录，不是已确认的现实事件 |
| `search_recent_alerts` | 查询当前房间近期同类别提醒 | 同类别只是查重线索；服务端仍比较事件并执行自己的重复提醒规则 |
| `inspect_live_frame` | 看当前截图或某条归档观测关联的截图 | 必须有视觉能力；每次调查最多成功检查一次；图片有体积限制 |
| `save_frame_evidence` | 将刚检查过且确有用的截图暂存在本次证据流程 | 只保存该调查明确选择的图片；临时文件随调查清理；不是无限期图片归档 |
| `create_alert` | 提出一条提醒 | 终端工具；需引用 1–6 条实际证据，标明依据来自当前信号还是历史；看过图且用到视觉结论时必须先保存该图，服务端再校验目标、证据、置信度、时效和重复项 |
| `request_user_input` | 某条规则确实取决于用户偏好时提问 | 终端工具；暂停的是当前 Investigation，不会停止整个 Run；同一 Run 只保留一个待答问题，后续待澄清信号并入该问题；普通证据不足不应该转成提问 |

`search_observations` 是按需工具，不是每次 Investigation 的固定步骤：当前信号足以判断时，Agent 可以直接结束或创建提醒；需要核对时间线、状态或反证时才检索。单次调查最多执行 6 次历史搜索，总工具调用默认最多 8 次、模型轮数最多 6 轮。Run 中的 `InvestigationMemory` 会直接作为有限历史线索注入，不会额外触发一次检索；它不能直接作为提醒证据。


例如，用户目标是“提醒我聊天区有人说某短语”。仅凭 OCR 出现相同词并不够：服务端还要确认 Agent 检查了对应画面，并且该文字和 OCR 来自同一张截图且位置属于可见聊天区。工具说明会告诉模型这些要求，Go 侧的工具 Handler 和最终提交门还会再次检查。

模型可提出结论，但没有任意 Shell、任意文件读写、随意控制浏览器、自动发言或交易工具。工具白名单是实际能力边界；提示词里写“请勿”并不是唯一的安全保护。

### 4.5 Service 与 Repository：把模型建议变成受校验的状态变化

`AgentReviewer` 返回 Decision 后，Service 在 Repository 更新中重新校验并保存调查结果；模型提出的 `alert` 只是申请，最终是否创建提醒由 Go 服务决定。证据时效、目标版本、视觉证据和重复提醒等提交条件见[架构文档的证据与提交章节](ARCHITECTURE.md#证据规则与提醒提交)。

## 5. 状态与生命周期

一次 `Run` 可以包含多条 `SignalEvent`、`Investigation` 和最终接受的 `Alert`。SQLite 会持久化尚未完成的 Pending 信号；重启后对仍有效的信号重新开始调查，但不恢复原模型会话或工具轮次。`Investigation` 的等待或失败不会自动停止 Run。对象字段、存储上限、观测流水与图片留存规则见[架构文档的跨调查上下文与持久化章节](ARCHITECTURE.md#跨调查上下文与持久化)。

## 6. 异步、超时、重试与幂等

### 接收与处理不是同一件事

有模型时，`SubmitSignal` 先校验并接收信号，成功后把工作交给后台队列并返回。HTTP 请求方断开不会取消已接受的任务，因为队列使用监控自己的 context。过期信号不再启动新调查；暂停、停止或修改目标会取消或使旧版本工作失效。队列容量、公平调度和信号有效期策略见[架构文档的有界队列与公平调度章节](ARCHITECTURE.md#有界队列与公平调度)。

举例：一条信号按目标版本 3 入队后，用户把目标改成版本 4。Service 会清理队列中的版本 3 项并取消正在执行的版本 3 调查；即使模型随后才返回，提交检查也会因版本不匹配而拒绝旧结论。

### 三种“重试”是三回事

| 类型 | 当前行为 | 为什么这样分开 |
|---|---|---|
| 模型 HTTP 传输重试 | 对可重放的请求，遇到有限的临时 HTTP 状态或瞬时网络错误时最多重试 1 次；遵守取消和总 deadline，并可使用短 `Retry-After` | 请求没有可靠响应时可重发同一个模型请求 |
| 模型格式修正 | Reviewer 对不符合预期的结构化输出请求最多修正 1 次，并计入原来的模型轮数 | 这是让模型纠正格式，不是网络重试 |
| 业务工具 / 提醒提交重试 | Harness 不自动重试；模型下一轮可能再次提出调用，但重复调用预算、业务门和幂等检查仍生效 | 搜索、写提醒等业务动作不能被当作可随意重放的 HTTP 读取请求 |

OpenAI 兼容客户端单次请求超时为 60 秒；Loop 调查默认 90 秒，单工具默认 12 秒；当前信号 deadline、Run 取消和调用者 context 还可能更早结束请求。具体哪个 deadline 先到，决定本次请求停止。请求日志会带调查 ID、轮次和超时来源，用来区分信号过期、调查总时限与 HTTP 客户端超时。

模型提供方还有一层熔断保护：默认连续 2 次模型失败后，熔断器开放 30 秒，期间新调查会快速失败，不继续向已知故障的模型发请求；冷却后只允许一个请求先试探恢复，成功会清零失败状态，失败则继续保护。已取消或信号超时这类不是提供方健康问题的结果不会记成模型失败。熔断保护减少无意义重试，但它不是服务恢复机制。

### 幂等：相同事件 ID 不应被当成新事件再次接收

每个信号带事件 ID 和内容指纹，Run 保存有限数量的接收回执。相同事件 ID 且内容一致会被识别为重复接收；同 ID 携带不同内容则是冲突。队列满时，Service 撤销尚未真正入队的信号及回执，所以同一个事件 ID 可以在背压解除后重试。这解决的是接收路径幂等，不代表所有外部调用都具备全局 exactly-once 语义。

提醒还有单独的重复抑制：模型工具会先查询近期提醒作为参考；最终 Service 仍按房间、事件类型和语义摘要校验重复项。工具被模型调用两次不等于一定产生两条提醒。Pending 信号保存在本机 SQLite，由当前 Go 进程消费；这不是跨机器分布式事务系统。

当前自动查重的简单例子是：同一房间两分钟内，如果新旧提醒摘要去掉空白和标点后完全一致，或者新信号文字与旧提醒引用的 OCR/ASR 文字完全一致，就认为是重复。它不等于通用的语义相似度模型；意思相近但换了说法的两条内容不保证自动合并。

有一个边界要特别讲准确：如果信号到达队列时已经超过有效期，Service 会保留信号记录、增加过期计数并释放临时图片，但 `SubmitSignal` 当前仍可能返回成功；这表示接收/留档流程处理了它，不代表进入队列或完成调查。调用方应结合监控的 Pending 状态理解处理结果，而不能把 HTTP 接收成功解释为“必然会出提醒”。

## 7. 上下文、图片和审计记录的真实边界

- 首轮最多带最近 6 条观测，每条文字最多 600 字符；历史查询最多 6 页、每页最多 12 条、每条源文字最多 400 字符。
- 每次调查最多带 5 条同目标版本、24 小时内的 `InvestigationMemory`；每条最多 3 条证据引用。记忆来自已完成调查，目标更新时清空；Agent 只能把它当历史线索，当前提醒仍需本次调查可验证的证据。
- 一次调查的历史查询结果累计最多 12,000 个 Unicode 字符。超预算时只返回能完整放入的记录，并告知模型停止继续翻页。
- 上述 12,000 字符预算**不含**系统提示、工具定义、图片、助手回复和其他上下文，因此它不是模型输入 token 的全局硬上限。
- 单轮模型输出最多 4,096 tokens。实际请求返回的输入/输出 token 计入 Review 指标和模型日志。
- 调查过程中的 `Observation` 暂时包含工具调用、工具输出和耗时并供下一轮使用；持久化的 `AgentStep` 记录工具名、用途、结果摘要、是否成功和耗时。Review 指标保存模型、token、总时延、轮数、停止原因、格式修正和传输重试。
- 当前持久化记录不保证保存完整的模型 prompt、每个工具原始参数和每段原始工具返回，也不提供一键重放一整次调查的能力。写项目能力时应说“保留工具步骤和运行指标”，不要说“完整保存所有 Agent 轨迹”。
- 图片会受图像大小、当前调查和临时文件生命周期约束。看图能力要以模型实际配置和归档证据为准，不能把 OCR 文字当作图片视觉结论。
- 从第 4 轮起，会尝试把较早的文字工具结果压缩成带 ID、来源和时间的摘要，并保留固定目标/计划前缀及最近工具往返；包含图片的调查跳过此压缩。它只缩短单次 Investigation 的模型会话，不等同于跨调查记忆，也不是全局 Token 硬上限。

这层记忆目前是“调查摘要”，不是实体级事件生命周期状态，也没有向量数据库或跨 Run 用户画像。效果仍需用固定事件集比较记忆启用前后的准确率、过时记忆误导率、延迟和 Token 成本后再宣称。

“异步任务”不等于“模型 token 流式输出”：调查由后台队列执行，前端通过 HTTP/SSE 接收监控状态更新；SSE 推的是状态变化，不是把模型正在生成的每个 token 逐字推到网页。

## 9. 面试讲解稿（约一分钟）

> 我这里说的 Harness 不是只有一个模型循环。`internal/agent/loop.go` 是通用内核，负责有限轮数、工具白名单、调用预算、重复调用检测、单工具和总超时，以及把工具结果放回下一轮。`internal/monitor/agent_reviewer.go` 把它接到 LiveGuard：准备每次调查的独立模型会话和上下文，挂上历史搜索、看图、查重和提醒工具，再把模型结果转成 Decision。外面的 Service 负责异步排队和并发，最后还会在 Go 侧校验目标版本、证据、时效和重复提醒，过了才写入 Repository。网络重试、格式修正和业务工具重试是分开的：传输最多重试一次，格式最多纠正一次，提醒不会被 Harness 自动重放。过程会保留步骤摘要、token、耗时和停止原因。验证方面有边界故障回归、mock 负载测量和真实运行耗时记录；固定文字评测链路仍需修复，mock 负载也不等于真实直播性能。

### 面试官追问时的准确回答

**“那 `loop.go` 为什么不直接做完所有事情？”**

> 因为它是通用循环，不应该知道直播证据、聊天区坐标或提醒重复规则。循环负责预算和执行；Monitor 层负责把合法的直播工具和业务校验接进来。这样循环逻辑能复用，领域规则也能在最终提交处再次验证。

**“模型是不是可以直接发提醒？”**

> 不能。模型最多调用白名单中的 `create_alert` 提出申请。工具 Handler 和 Service 都要校验证据；Service 还检查 Run 是否仍运行、目标版本是否过期、信号是否有效、是否重复。最终保存由 Repository 完成。

**“你怎么保证异步任务重试不会重复处理？”**

> 接收使用事件 ID 和 fingerprint 做幂等识别。队列满时会撤销未入队事件的回执，让生产方可以用相同 ID 重试；提醒提交又有独立查重。这个保证覆盖本地接收和提醒业务规则，不是跨机器 exactly-once。

**“你们测的 P95 是端到端 P95 吗？”**

> 不是一个统一端到端数字。当前有 mock Reviewer 下的同步 Ingest 与异步 SubmitSignal 排队/处理测量，也有固定文字模型调查的历史 P95。真实直播从源端发生、浏览器采集、OCR、模型、提交直到网页显示的整链路还需要单独测。
