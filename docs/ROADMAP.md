# LiveGuard 优化路线图

最后核对：2026-10-15

这份文档把当前能确认的问题和后续可做的改进放在一起，方便项目协作者讨论、拆分工作和检查结果。它记录的是**候选方向**，不代表已经排期或承诺完成时间。所有项目当前状态均为“候选，待讨论”。

## 怎么一起维护这份路线图

每个改进项都说明四件事：当前问题、代码或测量能证明什么、可以怎样改、怎样判断改动有效。开始实现前，协作者可以补充替代方案、依赖和工作量估计；方案确认后再更新状态。

| 状态 | 含义 |
|---|---|
| 候选 | 有问题依据，值得讨论；尚未决定是否做或何时做 |
| 已确认 | 方向和验收方式已经达成一致，但可能还没开始 |
| 进行中 | 已有人负责并开始实现；应补充负责人或相关分支/PR |
| 完成 | 实现已合并，且列出的测试或测量证据已经取得 |
| 暂缓 | 当前不做；写明原因，条件变化后再重新讨论 |

如果某项需要比较多种方案、会影响多个模块，先写一份具体 **RFC（征求意见稿）**，记录背景、候选设计、取舍和待回答的问题；讨论形成长期有效的技术决定后，再按需要写 **ADR（架构决定记录）**。路线图本身负责回答“有哪些问题值得改进”，不替代某项工作的设计稿、任务清单或决定记录。

## 候选改进

### 1. 测量直播采集能看到多少目标事件

**当前问题**：系统按间隔截图并识别文字，因此可能漏掉两次截图之间出现后又消失的评论，也看不到浏览器视口之外的内容。采集和 OCR 已分开运行，界面能显示截图次数、实际间隔、采集耗时和 OCR 积压跳过数；这些指标能提示处理变慢，却不能说明目标事件到底漏了多少。

**已有证据**：当前没有带已知答案的真实直播样本漏采率。合成输入和固定图片测试可以验证代码行为，不能证明真实直播覆盖率。

**可讨论的方向**：先定义“目标事件”的标注规则并构造带时间标注的回放样本，再只对获得明确许可、可用于项目评测的真实直播片段做小规模对照。报告应记录样本来源和范围，同时列出命中率、漏失案例、从事件出现到提醒的延迟、截图跳过和 OCR 积压，而不只放成功案例。

**完成证据**：别人可以按文档重跑评测；报告说明数据来源、样本数和限制，并能看出哪些事件被漏掉以及发生在哪个处理阶段。

**状态**：候选，待讨论。

### 2. 给长期观测数据制定留存和备份办法

**当前问题**：本机模式会把完整观测追加写入 `runtime/liveguard.json.observations.jsonl`。按当前“保留流水”的设计，观测不会自动清理，所以长时间运行会持续占用磁盘。

**重要边界**：当前调查使用的截图保存在临时文件中；`save_frame_evidence` 表示图片只在本次调查期间临时保留，正常结束时删除。当前路径会记录可能关联的文字证据和文字结论，不会把这张截图归档到 `runtime/frames`。进程被强制终止后的临时文件清理尚未专项验证。代码里保留了读取既有归档图的入口，但不能据此说新截图会被持续保存。

**可讨论的方向**：先展示观测流水的本机占用量，并确定用户可理解的保留策略，例如手动导出、按时间归档或在用户确认后清理。任何自动删除都需要先明确默认值、恢复方式和数据丢失提示。

**完成证据**：长时间合成运行能测出文件增长速度；备份与恢复步骤经过验证；若实现清理，测试能证明清理范围明确且不会误删仍被引用的数据。

**状态**：候选，待讨论。

### 3. 区分“匹配到几条观测”和“实际发生了几次事件”

**当前问题**：历史搜索返回的是符合文字和时间条件的观测记录数。同一事件可能被 OCR 多次记录，多个事件也可能使用相似文字；观测条数不能直接当作现实中事件次数。系统也没有统一记录“预告、开始、延期、取消、结束”属于同一事件的生命周期。

**已有边界**：单次调查的搜索最多 6 次、每页最多 12 条；一个查询最多提供 8 个候选短语。后端的 `total_matches` 表示满足筛选条件的观测记录总数，不是事件去重结果。

**可讨论的方向**：为跨时间推进的真实事件建立显式关联和状态变化记录，让“观测证据”与“事件”成为不同层次的数据。状态如何合并、更正或撤销需要先写清规则，避免模型仅凭文本相似就把两件事合成一件。

**完成证据**：测试覆盖预告后开始、延期、取消、更正，以及相似文字但属于不同事件的情况；查询结果明确区分观测数和事件数。

**状态**：候选，待讨论。

### 4. 扩展负载测量，覆盖排队与恢复过程

**当前问题**：有同步和异步合成负载工具，可以测提交吞吐、队列等待、复核耗时、背压和 P95 延迟。当前测量使用固定延迟的 mock Reviewer，不包括真实浏览器截图、OCR、持久化、网络或模型耗时，因此不能直接代表端到端生产性能。

**可讨论的方向**：增加持续运行、队列达到容量、服务恢复和不同输入速率下的测量；分别报告提交、等待、模型判断、保存和最终网页可见等阶段，避免把单阶段延迟说成完整提醒延迟。真实模型测量应与 mock 结果分开，并记录环境及调用成本。

**完成证据**：负载报告记录运行模式、请求数量、mock 延迟、运行环境和其他参数，有成功/过期/拒绝/失败数量、吞吐和 P50/P95 延迟；至少包含一次队列压力和恢复场景，并清楚标注 mock 与真实依赖的差别。报告口径与现有 `docs/EVALUATION.md` 对齐，便于前后比较。

**状态**：候选，待讨论。

### 5. 讨论单个监控会话的累计模型成本上限

**当前问题**：单次调查有轮数、调用次数和超时约束，模型请求也记录 token 和耗时；但目前没有每个 Run 或每日累计 token 的硬上限。长时间保持监控时，用户不容易预先知道累计调用成本。

**可讨论的方向**：比较仅显示累计用量、达到软阈值提醒，以及达到硬阈值暂停调查等方案。设计时需要说明模型无法准确预估费用时如何展示，达到上限后采集是否继续，以及用户怎样恢复。

**完成证据**：用户能查看累计用量和限制含义；超限行为有服务端测试覆盖；停止判断与继续采集等状态不会混淆。

**状态**：候选，待讨论。

### 6. 让故障提示直接告诉用户“哪里出错、下一步做什么”

**当前问题**：采集、识别、排队、模型判断和提醒保存是不同阶段。现有状态和日志能提供部分线索，但用户仍可能需要查日志才能判断故障点，或不知道应该重新登录、检查配置还是等待服务恢复。

**可讨论的方向**：为常见故障统一“发生阶段、用户可见说明、自动恢复行为、用户下一步”四项信息。把可以自动恢复的暂时故障与需要用户操作的登录/配置问题分开呈现。

**完成证据**：故障注入或单元测试覆盖各阶段代表性错误；网页显示与日志中的原因一致；操作文档给出可执行的恢复步骤。

**状态**：候选，待讨论。

## 建议的协作顺序

下面只是便于讨论的顺序，不是已批准的排期：

1. **先建立可信测量**：补齐采集覆盖与负载的可复现报告，避免后续优化只凭感觉。
2. **再讨论数据与事件模型**：明确观测留存策略，以及怎样表示现实事件的开始、变化和结束。
3. **最后完善长期运行体验**：根据用量和故障证据，设计成本提示、存储管理和恢复指引。

认领工作时，请把本页的候选项拆成清楚的小任务；如果实现中发现原问题描述不准确，先更新“当前问题”和证据，再调整方案。完成后把测试、评测报告或 PR 链接补回对应条目。
